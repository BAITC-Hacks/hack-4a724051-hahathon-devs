## 1. Что требует ТЗ

Цель: сократить время выбора товара и однотипные обращения к менеджерам. Пользователи: частные покупатели и закупщики организаций. Канал: единый чат на существующем сайте ekt.kz, desktop и mobile.

| Область | Требование и приёмка |
| --- | --- |
| Каталог | По существующему артикулу возвращать корректные характеристики, наличие и сертификат, если он есть в базе |
| Аналоги | При нулевом остатке предложить минимум один релевантный аналог с объяснением |
| Условия покупки | Содержательные ответы про оплату, доставку, минимальную партию |
| Корзина | Изменять только после явного подтверждения; учитывать количество и остаток |
| Переход к покупке | После добавления выдавать прямую ссылку на актуальную корзину/оформление |
| Ввод | Свободный текст, фото, Excel, Word, PDF, JPEG, контекст сессии |
| Скорость | Единицы секунд; точный SLA и отдельный бюджет обработки файлов не заданы |
| Артефакты | Репозиторий и README с архитектурой, запуском и описанием данных |

Файлы перечислены во входе задачи, хотя не выделены отдельным пунктом Must have. Не следует молча исключать их из объёма: для MVP согласовать форматы, размеры и способ обработки сложных файлов.

Опционально: казахский язык, сопутствующие товары, история для авторизованных пользователей, эскалация менеджеру. Сессионный контекст обязателен независимо от сохранения долговременной истории.

Запрещено: неподтверждённое изменение корзины/оформление заказа; недостоверные цена и наличие; запрос или хранение платёжных данных. Требуются приватность, защита действий, объяснение аналогов и совместимость с текущей платформой.

ТЗ допускает репрезентативный, анонимизированный или синтетический каталог для прототипа. Демонстрационные данные и интеграции следует обозначать явно.

## 2. Что реально предоставляет API

Второй документ содержит Basic Auth и три примера адресов: список, следующая страница списка, детальная карточка. Секреты в этот файл не перенесены.

| Запрос | Проверенный результат |
| --- | --- |
| `GET https://ekt.kz/api/products` | HTTP 200; `page=1`, `per_page=20`, `count=20`, массив `items` |
| `GET https://ekt.kz/api/products/detail?id=515291` | HTTP 200; описание, цена, общий остаток, склады, свойства |
| `GET /api/products?page=2` | Документирован в исходном документе; отдельно не вызывался |

Список: `id`, `name`, `article`, `price`, `image`, `url`, `url_api_detail`, `offers`. В проверенной странице нет остатков и полного набора характеристик. `count=20` нельзя интерпретировать как общий размер каталога: total в этом ответе не обнаружен.

Карточка: `id`, `name`, `article`, `description`, `price`, `quantity`, `stores`, `image`, `url`, `offers`, `properties`. Склады имеют `id`, `name`, `quantity`. В проверенной карточке `offers` пуст.

### Обнаруженный конфликт данных

Товар 515291, внутренний артикул `200300285_`, артикул поставщика `027228`:

- Название: автомат DRX250 MT, 160 А.
- Описание: номинальный ток 160 А.
- `properties.NOMINALNYY_TOK`: `250 А`.
- Цена в ответе: 64920; отдельного поля валюты в проверенном ответе нет.
- `quantity=23`; сумма складских количеств в этой карточке также 23.

Следствие: нельзя считать любое структурированное поле безусловно верным. Сохранять исходное значение, источник, нормализованное значение и статус конфликта. Не использовать спорный параметр как доказательство совместимости аналога. Правило выбора достоверного источника необходимо согласовать с партнёром.

### Неопределённости интеграции

1. В предоставленных документах нет API корзины, авторизации покупателя, резерва и оформления заказа. Это отсутствие документации, а не доказательство отсутствия таких API на сайте.
2. Не задокументированы поиск, фильтры, сортировка, total страниц, лимиты запросов, обновление по изменённым записям и гарантии свежести.
3. В проверенной карточке нет очевидного поля сертификата; нельзя распространять вывод на весь каталог.
4. Источник оплаты, доставки и минимальной партии не предоставлен. Есть `KRATNOST_MIN=1`, но точная семантика поля не описана.
5. В списке складов встречаются названия «Брак MEGALIGHT», «Образцы Отдел Закупа», «перемещение» и другие внутренние названия. Нужен согласованный список складов, доступных к продаже, и правила выдачи клиенту складской информации.
6. `RECOMMEND` содержит ID других товаров, но документ не определяет их как аналоги. Не использовать это поле как готовую таблицу совместимости.
7. `id`, внутренний `article`, артикул поставщика и штрихкод — разные идентификаторы. Хранить их отдельно; строки с нулями и суффиксами не превращать в числа.
8. Структура ссылок `/upload/iblock/` и свойства CML2 похожи на Bitrix. Это косвенный признак; платформу и версию должен подтвердить партнёр.

## 3. Как устроен продукт YOU.AERO по публичным материалам

Это закрытый пилот рабочего пространства авиационных закупок. Публичный сайт объясняет продукт; реальные компании, результаты поиска, запросы, ответы и документы находятся в защищённом приложении. Публичная демонстрация Marketplace использует синтетические идентификаторы и не показывает живой склад.

Сценарий покупателя: исходный номер детали/потребность → поиск → структурированный RFQ (запрос предложения) → ответы поставщиков → сравнение и проверка документов → решение уполномоченного человека. RFQ не является заказом.

Сценарий поставщика: сведения об остатках и компании → сопоставление с RFQ → подготовка ответа и документов → проверка человеком. Наличие профиля не означает универсального подтверждения надёжности поставщика.

По FAQ, приём платежей, escrow, кошельки и выплаты поставщикам в пилоте недоступны. Аукционы — planned; market intelligence — concept; интеграции — planned/discovery. Публичная страница интеграций прямо не представляет ERP, marketplace, Azure, logistics или vendor connectors как работающие.

Сквозной принцип: контекст потребности и источники данных сохраняются в структурированных результатах; существенные решения остаются у людей. Это публичное описание продукта, а не доказательство конкретной внутренней программной архитектуры.

## 5. Предварительные архитектурные выводы для ekt.kz

Ниже наши предложения, не требования исходного ТЗ и не реконструкция кода YOU.AERO.

### Разделить ответственность

1. Единый чат с контекстом и карточками товаров.
2. Оркестратор: определяет запрос, уточняет недостающие параметры, вызывает разрешённые инструменты.
3. Поиск каталога: точные идентификаторы, текстовый поиск, нормализованные фильтры; семантический поиск можно добавлять для свободных формулировок.
4. Проверка и подбор аналогов: обязательные ограничения категории, конфликты, источники и объяснение совпадений/различий.
5. База условий покупки: утверждённые документы с источниками и актуальностью.
6. Обработка файлов: извлечение строк и характеристик, отметка неопределённости, связь с исходными страницами/ячейками.
7. Сервис корзины: серверная проверка подтверждения, сессии, количества и результата операции.

Для MVP разумный кандидат — модульное приложение и отдельный обработчик тяжёлых файлов. Шесть автономных агентов или микросервисов пока не обоснованы требованиями. Число модулей не обязано совпадать с числом LLM-вызовов.

### Источники фактов

- Поисковый индекс помогает найти кандидатов; цену и наличие проверять по источнику актуальных данных.
- Не отвечать об отсутствии товара только потому, что не сработал поиск.
- При сбое API различать «наличие неизвестно» и «остаток равен нулю».
- Для обычного вопроса не обходить все страницы каталога: подготовить индекс заранее; синхронизация зависит от лимитов и API обновлений.
- Цены, количество и арифметику обрабатывать кодом; модель формулирует ответ по проверенным результатам.
- Для файлов: исходник → извлечённые позиции → уточнение неоднозначностей → поиск → предложение. Инструкции внутри вложений не дают права менять корзину.
- Аналог: обязательные параметры категории → допустимые кандидаты → доступность → ранжирование → объяснение. Текстовая похожесть и поле RECOMMEND не доказывают взаимозаменяемость.
- Если подходящий аналог не найден, сообщать об этом. Для выполнения демонстрационной приёмки подготовить реальные проверенные пары, а не выдумывать замену.

### Подтверждение корзины как состояние

Предлагаемый процесс: DRAFT → AWAITING_CONFIRMATION → CONFIRMED → REVALIDATING → APPLIED / NEEDS_RECONFIRMATION / FAILED.

Предложение содержит ID товаров/вариантов, количества, цены, складской контекст и срок действия. Подтверждение связывается с конкретной версией предложения и сессией. Неоднозначное «да» без актуального предложения не является разрешением на произвольную операцию.

После подтверждения: повторно проверить наличие/условия, выполнить операцию один раз, прочитать актуальное состояние корзины, выдать корректную ссылку. При существенном изменении состава, количества или цены показать обновлённое предложение. Повтор запроса после сетевого сбоя не должен дублировать товар. Учесть уже находящееся в корзине количество и продажи другим клиентам; строгая гарантия доступности зависит от атомарности платформы/резервов.

Проверка разрешений должна выполняться сервером независимо от ответа LLM. Basic Auth каталога доступен только backend, не браузеру и не содержимому промптов. Платёжные реквизиты не собираются.

### Что взять у YOU.AERO

Переносим: структурированный контекст между этапами, результаты со ссылками на источники, явные границы полномочий, ручное подтверждение действий, журнал операций и статусы неопределённости.

Для MVP ekt.kz наиболее полезны идеи Ella (поиск/спецификации), TANGO (проверка данных/документов), OSCAR (контролируемое действие). Из VICTOR — подготовка предложения покупателю. LINA может вдохновить подсказки в чате; RAY — последующую аналитику неудовлетворённого спроса. Полный авиационный RFQ-маркетплейс значительно шире задачи интернет-магазина.

| Повтор HTTP-запроса | Нет повторного добавления той же операции |
| Неоднозначное название/артикул на фото | Уточнение, отсутствие уверенного вымышленного совпадения |
| API недоступен | Сообщение об отсутствии актуальной проверки, запрет неподтверждённого действия |
| Другая сессия/чужое подтверждение | Отказ в изменении корзины |
| Текст-инструкция внутри PDF | Обрабатывается как данные, не как разрешение выполнить действие |

Для скорости измерять отдельно обычный текстовый ответ, получение карточки/наличия и обработку большого файла. Уточнить численные цели p95, объём каталога и конкурентную нагрузку до выбора инфраструктуры.

## 7. Открытые вопросы для совместного проектирования

1. Первый результат — отдельное хакатонное демо или встроенный виджет с реальной корзиной ekt.kz?
2. Каков срок, состав команды и бюджет инфраструктуры/моделей?
3. Каковы платформа сайта, API корзины, идентификатор покупательской сессии и допустимый способ встраивания?
4. Какие склады продающие, как учитывать резервы, единицы измерения, упаковки и минимальное количество?
5. Где брать утверждённые условия покупки и сертификаты?
6. Кто определяет обязательные параметры аналогов и разрешает противоречия каталога?
7. Каковы объём каталога, частота обновлений и лимиты API?
8. Какие ограничения у файлов: размер, страницы, строки, срок хранения и персональные данные?

Первое решение, которое меняет архитектуру сильнее выбора фреймворка: реальная интеграция с корзиной или явно обозначенная демонстрационная корзина через заменяемый адаптер.
