# План улучшенного MVP на 5 часов

Это timebox реализации после согласования архитектуры, а не обещание production-ready системы. Стек и границы: [architecture.md](architecture.md). Выполненная текущая работа: исследование, архитектурные документы, .gitignore, .env.example. Приложение ещё не реализовано.

## Демонстрируемый результат

Покупатель в одном интерфейсе ищет товар по артикулу/описанию, видит проверенные характеристики и наличие, получает объяснение аналога из подготовленной проверенной выборки, задаёт вопрос об условиях покупки, подтверждает конкретное предложение и открывает актуальную **демонстрационную** корзину. Документы дают позиции с указанием происхождения и непрочитанных фрагментов. Реальные цена и наличие не подменяются синтетическими незаметно для пользователя.

План рассчитан на узкую реализацию с готовой средой и доступами; неизвестные API и инфраструктура не считаются решёнными временем в таблице. При затруднениях уменьшаем объём функций через явно видимые статусы; не убираем ownership, подтверждение, проверку фактов и лимиты. Сначала работает полный сценарий «поиск → предложение → подтверждение → корзина», затем расширяем файлы и ответы.

## Что откладываем первым

SSE вместо polling; анимации и персонажи; казахский язык; долговременная память; проактивные подсказки; маркетинговая аналитика; автоматическое обучение аналогам; сложные embeddings; универсальная платформа шести агентов; multi-tenancy; реальный checkout без API. Связь с менеджером может быть понятным следующим шагом без автоматической отправки сообщений.

## Минимальные проверки до демо

### Каталог и качество

- Известный внутренний и поставщицкий артикул находят нужный ID без потери ведущих нулей.
- Отсутствие в частичном индексе не выдаётся за отсутствие во всём магазине.
- Конфликт 160/250 А отображён; такой параметр не подтверждает аналог.
- Остаток 0, неизвестный остаток и timeout различаются.
- Сертификат выдаётся только по действительному источнику; ссылка не выдумывается.
- Аналог из curated набора имеет реальное основание и проверенное наличие; демо-связь обозначена как демо до согласования владельцем.

### Действия и изоляция

- «Расскажи про товар» и предложенный моделью action не изменяют корзину.
- Подтверждение привязано к session + proposal + version + TTL.
- Повтор с тем же Idempotency-Key и телом возвращает тот же результат; другое тело — 409.
- Два одновременных подтверждения не дублируют применение.
- Другая сессия не читает turn, asset, proposal или корзину; CSRF/Origin проверяются.
- Изменение цены/остатка требует нового предложения. Дробное/отрицательное количество не округляется в допустимое молча.

### ИИ, файлы и отказы

- `LLM_ENABLED=false` и пустой ключ дают ноль обращений к провайдеру.
- Инструкция из description/PDF не разрешает новый tool, URL, запись или раскрытие секрета.
- Невалидная схема/цитата не публикует неподтверждённую цену или действие.
- Исчерпанный site/session budget блокирует следующий вызов, в том числе при конкуренции worker.
- Scanner pending/unavailable не допускает парсинг; oversized/zip bomb/неверный MIME отклоняются.
- Каждый файл имеет статус; превышение лимита страниц/строк видно.
- Перезапуск worker не теряет committed job; платный вызов с неизвестным исходом не повторяется автоматически.
- LLM/EKT timeout приводит к понятному ограничению; поиск по индексу сохраняется.

## Условия перехода от демо к реальной интеграции

От партнёра нужны: контракт корзины и сессии покупателя, резервирование/идемпотентность/сверка, валюта и единицы, продаваемые склады, схема сертификатов и offers, достоверный источник условий, подтверждённые аналоги и правило разрешения конфликтов. Реальный CartPort включается только после контрактных проверок. Публичные загрузки — только после готовности защиты файлов и согласованной политики данных.

README запуска, locked зависимости, миграции и измеренные latency появляются вместе с реализацией; их не следует заменять придуманными командами или цифрами.
